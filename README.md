# 虚拟机备份维护台

基于 FastAPI 的快照链维护工具：值班员从网页导入 JSON 备份清单（基盘 + 可分叉的增量快照），
可以撤除有子层的非根快照（只重写直接子层），从任一可用快照下载还原后的原始磁盘镜像，
并把任一恢复点及其全部祖先层**分层同步到备用卷 /replica**，再从副本下载链上任一恢复点。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

网页操作：「载入示例清单」→「导入」→ 在快照树上点「同步到备用卷」（可对多个分支各同步一次）
→ 在「备用卷副本」区点「下载副本镜像」；也可继续「撤除」或「下载镜像」。

本地开发（不用 Docker）：

```bash
pip install -r requirements-dev.txt
python -m pytest tests/ -q          # 跑测试
DATA_DIR=./data REPLICA_DIR=./replica uvicorn app.main:app --port 8000
```

## 数据模型

- 单盘 ≤ 16 MiB，盘块 4 KiB，清单中块数据为 Base64（解码后必须正好 4096 字节）。
- 清单 `{"disk_size": N, "layers": [{"id", "parent", "blocks": {"块索引": "base64"}}]}`，
  构成一棵（或多棵）快照树；块索引从 0 到 `disk_size/4096 - 1`。
- 稀疏语义：某快照在某块上没有数据时向父层继承；**显式写入的全零块视为改写**，会盖住父层数据。
- 存储布局（`DATA_DIR`，容器内为 `/data` 卷）：

```
manifest.json    当前清单：epoch、disk_size、每层 {parent, file, blocks}（原子替换更新）
journal.json     撤除操作的两阶段日志，仅在操作进行中存在
layers/<uuid>.layer   每层一个文件：{"blocks": {"索引": "base64"}}
```

层文件按 uuid 命名、写一次后不再修改；撤除产生的新子层写为新文件，绝不就地改旧文件。

## 撤除（remove）语义

目标必须是非根且有直接子层的快照。对每个直接子层 C：

```
新C.blocks = C.blocks ∪ (目标.blocks 中 C 没有的块)   # 缺块才继承；全零块算改写，保留子层版本
新C.parent = 目标.parent
```

孙层及更远的层完全不动。可证明每个保留恢复点还原出的字节与撤除前一致：
对任意块，若子层自有 → 仍是子层的值；否则若目标层有 → 合并后取目标的值；否则继续向祖父层继承。

## 一致性与崩溃恢复

撤除按以下顺序执行，**第 3 步是唯一的提交点**：

1. 为每个直接子层写出合并后的新层文件（tmp + rename + fsync）——失败则清理半成品，旧链未受影响；
2. 写 `journal.json`（旧/新 epoch、新文件、待删旧文件、完整新清单）；
3. 原子替换 `manifest.json` —— 提交点，失败则回滚（删新文件与 journal），旧链仍可用；
4. 删除旧层文件与 journal（收尾失败不影响一致性）。

进程中断并重启后，启动恢复保证网页只呈现一套完整可恢复的链：

| 现场 | 判定 | 动作 |
|---|---|---|
| journal 有效，manifest 仍是旧 epoch | 崩溃在提交点前 | 回滚：删新文件，保留旧链 |
| journal 有效，manifest 已是新 epoch | 崩溃在提交点后 | 前滚：补删旧文件 |
| journal 缺失/损坏 | 无在途操作（日志先于清单写） | 清理孤儿/临时层文件 |

恢复事件会在网页顶部展示。导入同样原子：新层文件全部落盘后才替换 manifest，
崩溃残留由启动时的孤儿清理回收。

## 分层副本同步（备用卷 /replica）

值班员在源卷快照树上选择一个恢复点，服务把**该点及其全部祖先层**按原父子关系复制到备用卷
（`REPLICA_DIR`，容器内 `/replica`，compose 中为独立命名卷 `backup-replica`），
副本链上的任一恢复点都能下载还原镜像。

副本卷布局：

```
manifest.json    副本清单：disk_size + 每条已提交的同步链（sync_id、来源 epoch、层序与父子关系）
journal.json     同步操作的两阶段日志，仅在操作进行中存在
layers/<sha256>.layer   内容寻址的层文件，逐字节复制自源卷，写一次后不可变
```

设计要点：

- **稀疏块保留**：层文件逐字节复制（仍是 `{"blocks": {索引: base64}}` 的稀疏表示），
  不物化整盘、不合并父层；副本还原沿父子链合并，语义与源卷完全一致。
- **层复用**：层文件以内容 sha256 命名并跨所有同步链共享。同一来源 epoch 再次同步另一分支时，
  已复制的祖先层命中哈希直接复用，只写分支上的新层；同一恢复点重复同步幂等不增文件。
  不同 epoch 即使层 id 相同，内容不同即哈希不同，互不覆盖。
- **源卷只读**：同步通过 `Store.snapshot_chain()` 在源卷锁内取一致快照（层元数据 + 层文件原始字节），
  全程不修改源卷；锁顺序固定“源 → 副本”，同步后源卷的撤除/下载照常工作。

同步按以下顺序执行，**第 3 步是唯一的提交点**：

1. 逐字节复制缺失的层文件（tmp + rename + fsync；哈希已存在则复用）——失败则清理本次新文件，旧链未受影响；
2. 写 `journal.json`（sync_id、本次新文件、完整新清单）；
3. 原子替换副本 `manifest.json` —— 提交点，失败则回滚（删本次新文件与 journal），同步前的链仍可用；
4. 删除 journal（收尾失败不影响一致性）。

因此复制或写清单失败、进程重启后，备用卷只呈现**同步前**或**完整的新链**两种状态：

| 现场 | 判定 | 动作 |
|---|---|---|
| journal 有效，清单已含本次 sync_id | 崩溃在提交点后 | 前滚：清理 journal，新链生效 |
| journal 有效，清单不含 sync_id | 崩溃在提交点前 | 回滚：删本次新文件（保留仍被旧链引用的共享层），旧链原样保留 |
| journal 缺失/损坏 | 同步未开始（日志先于清单写） | 清理临时/孤儿层文件 |

副本恢复事件同样展示在网页的「备用卷副本」区。

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 维护网页 |
| GET | `/api/state` | 当前链状态（层、父子关系、可撤除标记、恢复事件） |
| GET | `/api/sample` | 生成一份示例清单 |
| POST | `/api/import` | 导入清单（整体替换，原子切换） |
| POST | `/api/remove/{id}` | 撤除有子层的非根快照 |
| GET | `/api/download/{id}` | 下载该快照还原出的原始镜像（`.raw`） |
| GET | `/api/replica/state` | 备用卷副本状态（同步链、去重层文件数、恢复事件） |
| POST | `/api/replica/sync/{id}` | 把该恢复点及全部祖先层同步到备用卷（返回新复制/复用层数） |
| GET | `/api/replica/download/{sync_id}/{id}` | 从指定副本链下载某恢复点的原始镜像（`.raw`） |

## 测试

`tests/` 共 82 个用例。原有用例覆盖：导入校验（尺寸/索引/base64/环/重复）、各层还原字节与独立解析器一致、
全零块改写、稀疏继承、撤除后字节不变与重挂链、只重写直接子层、提交点前/后崩溃恢复、
写盘失败回滚、孤儿文件清理、API 全流程与错误码。

新增副本用例（`tests/test_replica.py` 与 `test_api.py::TestReplicaApi`）覆盖：祖先链复制与父子关系保持、
副本每个恢复点字节与源卷/独立解析器一致、稀疏块不物化、层文件逐字节相同且内容寻址、
同 epoch 跨分支层复用与共享物理文件、重复同步幂等、不同 epoch 同名层不冲突、
提交点前/后崩溃的回滚与前滚（含第一条链保留）、损坏 journal、孤儿清理、
写清单/写层失败回滚、盘大小不一致拒绝、源卷字节不变、副本下载 404 与 API 全流程。

## 已知限制（后续工作）

- 单进程 + 内存锁，未做多实例并发；层文件为 JSON 存 base64，未做二进制压缩/去重
  （副本卷已按内容哈希去重，源卷层文件尚未去重）；
- 撤除仅限“有子层的非根快照”，不支持删除叶子快照与整树删除；
- 副本同步只增不删：备用卷不提供删除同步链/GC 整条链的接口，孤儿文件仅在启动恢复时清理；
  不同盘大小的清单不能同步进同一备用卷；
- 清单体积未设上限（16 MiB 盘 × 层数的 base64 全量提交），大清单导入会占用较多内存；
- 未做认证鉴权，仅限内网/演示用途。
